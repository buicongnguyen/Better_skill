복사해서 쓰는 프롬프트

빠른 요약의 각 단계에 대응하는 예제 프롬프트입니다.

환경 설정부터 시작하세요. 이 독창적 예제는 Signal Garden 규칙을 따릅니다.

게임 폴더에 연결된 채팅에 한 번에 하나씩 붙여 넣고 결과를 확인한 다음 진행하세요. 예제를 바꿀 때는 합의한 자신의 요구 사항을 유지하세요.

제안된 절차이며 벤치마크나 한 프롬프트로 완성된 게임을 얻는다는 보장은 아닙니다.

저장소·실행 도구가 없는 챗봇은 명세나 프롬프트 작성을 돕지만 로컬 코드 검사, 테스트, 공개는 할 수 없습니다. 해당 단계에는 폴더와 필요한 도구에 접근하는 코딩 에이전트를 사용하세요.

Claude Code에서는 제공되는 Claude 모델을 사용합니다. 프롬프트에 “Astra”라고 적어도 모델이 바뀌지 않습니다.

프로젝트 파일을 지속적인 기준으로 유지하세요. {{cite:56}} {{cite:57}}

처음의 짧은 블록만 바꾸고 상세 지침은 유지하기

  1. 전체 프롬프트를 아직 보내지 않은 채팅 초안에 복사하세요. 그다음 시작 블록을 수정하고 제목과 줄바꿈을 유지하세요.
  2. 시작 매개변수를 수정하세요. 에이전트 하나와 선택지가 있는 경우 엔진 또는 영상 도구 하나를 고르세요. 프로젝트에 맞는 나머지 기본값은 유지합니다.
  3. 실제 환경과 맞추세요. 앱에서 모델을 선택하고 올바른 폴더를 여세요. 모델이나 도구 이름을 입력해도 자동으로 활성화되지 않습니다.
  4. 하나의 기준 규칙을 유지하세요. 명세 작성 때 설계 변경을 RULE_CHANGES에 적고 이후 단계는 합의한 문서를 사용하세요. 엔진을 바꾸려면 기존 작업과 먼저 조정해야 합니다.
  5. 확인한 다음 계속하세요. 결과를 완료 조건과 비교합니다. 출시 프롬프트의 PUBLISH: YES는 명시한 대상 공개를 승인하며 NO는 로컬 준비만 뜻합니다.

RTS 계획 예제에서 배운 점

제공된 RTS 계획은 범위, 작업 묶음, 조정값, 완료 검사를 분리합니다. 이 책은 매개변수 → 목표 → 작업과 제약 → 완료 조건 구조를 적용합니다.

전체 게임 명세는 프로젝트 문서에 둡니다. 후속 프롬프트는 다음 유용한 결과를 요청하고 해당 문서를 참조하세요. 필수 게임 규칙은 명확히 하되 일상적인 구현 세부 사항은 에이전트가 선택하게 합니다. 항목이 많아진 것만으로 더 좋은 게임이 입증되지는 않습니다. {{cite:17}}

선택: PLAN.md를 만드는 프롬프트 하나

유용한 아이디어입니다. RTS 예제처럼 계획 문서를 요청하고 검토한 뒤 에이전트에게 구현을 맡길 수 있습니다. 기존 프롬프트 설계자는 실행 프롬프트를 만들고, 이 예제는 계획 자체를 만듭니다.

개선점은 작고 완결된 V1과 후속 목표를 나누고, 가정과 조정값을 표시하며, 필수 요구마다 확인 항목을 연결하는 것입니다. 보기 좋은 개요나 모델의 자기 평가는 실현 가능성이나 재미를 입증하지 않습니다. 이 형식은 독창적 제안입니다. 현재 Astra 지침은 집중된 지시와 명확한 완료 경계를 뒷받침하지만 이 템플릿의 우위를 측정한 근거는 아닙니다. {{cite:17}} {{cite:52}}

기본값으로 시도하세요. 전체 블록을 새 채팅의 아직 보내지 않은 초안에 복사하세요. 작은 RTS를 설명하므로 비공개 참조 파일이 필요하지 않습니다. 앱에서 모델을 선택하고 시작 값을 수정한 뒤 전송하세요. 파일 도구가 없는 챗봇에서는 OUTPUT_MODE: CHAT을 쓰고 받은 Markdown을 PLAN.md로 저장하세요. 코딩 에이전트는 의도한 프로젝트 폴더에서 FILE을 쓸 수 있습니다.

이것은 별도의 RTS 연습입니다. Signal Garden에 쓰려면 GAME_IDEA, V1_SCOPE 및 관련 매개변수를 합의한 명세로 바꾸세요. 아래 예제를 계속하기 전에 수락한 계획과 기존 프로젝트 문서를 일치시키세요.

{{prompt:plan-generator.md}}

예상 결과: 구현 작업 묶음, 의존 관계, 조정값 표, 요구와 검사 연결, 마일스톤, 출처, 미해결 위험을 담은 완전한 Markdown 계획입니다. 구현 전에 계획 단계에서 멈춥니다.

계획을 직접 검사하기

  1. 일관성 확인: 엔진과 대상이 하나이며 V1 제외 사항을 지키고 참조 파일에 의존하지 않는지 보세요. 계획한 일을 이미 통과했다고 하면 안 됩니다.
  2. 요구 하나 추적: 관련 작업과 검사를 찾으세요. 생산에서는 비용 차감 시점, 취소 환불, 두 번째 환불을 막는 규칙을 확인하세요.
  3. 매개변수 변경: ASSET_TOOL: PRIMITIVES로 별도 후보를 만드세요. Blender는 선택 사항이 되고 필수 가져오기와 마일스톤도 일치해야 합니다. 이전 계획을 비교용으로 보관하세요.
  4. 필요하면 비교: 별도의 새 채팅에서 프로젝트 사실, 모델, 도구, 예산을 같게 두고 이 템플릿과 “이 사실로 개발 계획을 작성하세요” 같은 짧은 요청을 비교하세요. 모순, 빠진 의존 관계, 범위 확대, 관찰 가능한 검사를 평가하고 반복한 뒤에야 신뢰할 만한 프롬프트 우위를 주장하세요.
  5. 다음은 실현 가능성 검사: 계획을 수락한 뒤 최소 장면/내보내기 실험을 별도로 승인하세요. 실제 작동 결과를 기록하고 관련 가정을 수정하세요. 문서 검토가 실험이나 사람의 플레이테스트를 대신할 수는 없습니다.

이 새 예제를 검증하기 위한 독립 모델 시험이나 게임 구현은 실행하지 않았습니다. 개선 장을 참고해 프롬프트 버전과 측정 결과를 따로 추적하세요. {{cite:52}}
