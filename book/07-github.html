Give the work a memory

The repository is the handoff between yesterday and tomorrow.

  • Git records local history.
  • GitHub holds a remote copy, review conversations, issues, and automation.
  • GitHub Pages serves the published game or book.

Keeping those roles separate makes debugging easier: a local commit is not a push, a push is not a successful deployment, and a deployment is not proof that the game is playable.

Step 1: establish a clean starting point

In a new empty game folder, initialize Git on main. If the folder is already a repository, inspect its status and preserve the current work instead.

Install Git and GitHub CLI, and authenticate GitHub CLI before creating a remote. The following commands are an example for a new Signal Garden project; replace the account name first. {{cite:39}} {{cite:40}}

git init -b main
git status --short
# Create the README, .gitignore, game brief, and project files.
# Review ignore rules and all scaffolded files before staging.
git status --short
git add --all
git diff --cached --stat
git diff --cached
git commit -m "chore: establish the Signal Garden baseline"
gh repo create YOUR_ACCOUNT/signal-garden --public --source=. --remote=origin
git push -u origin main

In this new project, stage the complete scaffold, including index.html, configuration files, and required assets. The two diff commands show its file summary and actual staged content.

Set ignore rules for dependencies, local environment files, and build output as appropriate before staging. In an existing repository, stage only the intended paths so unrelated work stays separate.

A public repository and Pages site publish the selected files; keep credentials and unlicensed assets out of the commit. {{cite:39}}

Step 2: keep the important decisions in files

signal-garden/
  AGENTS.md                     # Optional short project conventions
  .agents/skills/signal-garden-round-review/
    SKILL.md                    # Optional; only if it adds proven value
  docs/
    game-brief.md               # Player promise and constraints
    acceptance.md               # Observable completion conditions
    decisions.md                # Choices and reasons
    progress.md                 # Current state and next step
    playtests/                  # Human observations and evidence links
  src/
    game/                       # State, input, simulation
    render/                     # Scene, camera, visual feedback
    ui/                         # Instructions, HUD, result screens
  public/assets/
    credits.md                  # Asset provenance and license notes
  tests/                        # Focused behavior checks
  .github/workflows/pages.yml
  package.json
  package-lock.json

This structure is a starting proposal, not a demand to create empty abstractions. A tiny build can begin with fewer modules. Separate systems when their responsibilities become clear, especially if simulation logic is difficult to test because it is mixed with rendering code.

Step 3: make a checkpoint per meaningful change

A useful commit says what behavior now works: feat: collect cells and power the beacon is better than update. Save a known working baseline before trying an uncertain idea.

This example improves readability while preserving Signal Garden’s fixed camera. The switch reference documents creating its branch.

Create the named playtest file with your observations, and adapt the paths to the actual project. {{cite:39}}

git switch -c experiment/camera-readability
# Adjust the fixed camera framing, then playtest the obstructed route.
git diff
git add src/render/camera.ts docs/playtests/camera-readability.md
git diff --cached
git commit -m "fix: keep the robot visible behind the north planter"
git push -u origin experiment/camera-readability
# Write docs/pr-camera.md with the problem, change, and checks first.
gh pr create --base main --head experiment/camera-readability --title "Improve fixed camera readability" --body-file docs/pr-camera.md

The --body-file option reads an existing file; it does not create the description for you. The PR should state the player-visible problem, change, and checks.

For a solo experiment, a branch and reviewed commit may be enough. Use a PR when review or CI gates add value. {{cite:41}}

Step 4: leave a short continuation note

At the end of a session, update progress.md with the current commit, working behavior, known failure, launch command, and one next milestone. Anthropic’s long-running-agent report uses progress artifacts and Git history to reduce the need for a new session to reconstruct previous work. {{cite:05}}

When a bad change has already been shared, git revert creates a new commit that undoes it while preserving history. Inspect dependencies between commits and resolve any conflicts before completing the revert.

For an uncommitted experiment, show the exact diff and restore only the intended changes; unrelated work may be present. {{cite:39}}
