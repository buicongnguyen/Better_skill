Publish and close the loop

A release is a working URL and a recoverable revision.

For the proposed Vite game, GitHub Pages serves the built static files. It does not run a Node server or store private API keys. The example requires no backend: game logic executes in the browser, and the first release has no accounts or online service dependency.

1 · Configure the repository path

A project called signal-garden normally appears at https://YOUR_ACCOUNT.github.io/signal-garden/. In Vite, set the base path accordingly. A user site at the domain root uses a different base. The repository name’s case and asset filenames must be correct on the deployed host. {{cite:12}}

// vite.config.ts — example for the game repository
import { defineConfig } from 'vite';

export default defineConfig({
  base: '/signal-garden/',
});

Test the production build under this subpath before publication. Prefer imported assets or base-aware URLs. A path that works at localhost/ may fail when the application lives one directory below the domain root.

2 · Build, upload, deploy

In the repository’s Pages settings, choose GitHub Actions as the source. A Pages workflow builds the site, uploads its public artifact, and deploys it with the appropriate Pages and identity-token permissions. Use the github-pages environment and the URL returned by the deployment step. {{cite:13}}

This book’s actual workflow is a small static-site example. A Vite game should install from its lockfile and run its own checks before uploading dist. Pin reviewed action versions or commit SHAs, and check current official examples when adapting the workflow.

3 · Make publication explicit

After the game works locally, replace the account and repository placeholders in this release prompt. Its publication permission applies only after you actually send it with the intended destination.

{{prompt:release-prompt.md}}

4 · Verify the public result

  1. Confirm the push reached the intended remote and branch.
  2. Inspect the workflow run for that commit. A queued run is not a successful deployment.
  3. Open the deployment URL and check the production asset requests.
  4. Play a win path and a loss path, then restart. Repeat a pause/resume check.
  5. Record the deployed commit, controls, target browser, and any remaining limitations in the release note.

If deployment fails, inspect its logs and fix the specific cause. For a missing asset, check the base path and filename case. For a Godot export, check the renderer, exported filenames, and browser requirements. For a permissions error, inspect the Pages source, workflow permissions, and repository settings before changing unrelated code.

5 · Keep a path back

Record the last verified release revision. If a new release breaks the game, revert the responsible change in a new commit and allow the workflow to publish the repaired state. Check the resulting live URL again. A rollback command is only a step toward restoration.

The complete workflow

Choose a player experience → compare relevant approaches → verify current sources → establish the repository and brief → use available skills when relevant → choose a compact or bootstrap prompt → build playable checkpoints → test the real game → publish → retain only workflow changes that help.

The durable result is more than a game. It is a process that makes your next attempt easier to understand, easier to review, and easier to improve.
