Think, decide, improve

Make the next decision visible.

A useful thinking flow shows the outcome, the uncertainty, the action, and the evidence that changes the plan. These are observable working decisions, not a reconstruction of a model’s private reasoning.

The diagrams below are original proposals for this book. Use them to discuss work with Astra and to review what happened afterward.

Read and reuse the diagrams

Rectangles name actions or artifacts; diamonds name decisions; labeled arrows show the condition or information that moves work forward. A loop means that new evidence may change the next action.

It does not mean “repeat forever.” Set a completion condition and an effort limit for an experiment.

1 · The thinking and decision loop

{{diagram:thinking-loop}}

Signal Garden example: “The player loses sight of the robot behind the north planter” is a useful observation. First reproduce that route.

Compare a camera adjustment with a small occlusion treatment, then choose the smallest change that keeps the robot readable. Stop when the named route and nearby routes work; adding enemies does not resolve this uncertainty.

Ask Astra for a concise decision record: what changed, what evidence supports it, which uncertainty remains, and what happens next. A lengthy explanation is not a substitute for a playable result. The process can be lightweight for a small edit and more explicit when a decision affects the whole game.

2 · The data flow: prompts, context, skills, and tools

{{diagram:context-data}}
  • The brief supplies the desired experience.
  • Repository files supply actual rules and implementation.
  • A relevant skill may supply a reusable procedure.
  • A tool performs an action.
  • Results return as evidence for another decision.

This separation helps diagnose failures: a better prompt cannot grant missing browser access, and adding an API connection does not settle an ambiguous game rule.

3 · Decide what to add

{{diagram:choose-help}}

Before writing a new skill, inspect the agent’s actual capabilities. Is the existing skill available?

Was it selected? Does it contain the missing knowledge?

The skills chapter explains a controlled comparison. Astra’s current guidance supports reassessing overlapping instructions, while leaving room for specialized procedures. {{cite:17}}

For video work, this question becomes concrete.

  • A Remotion skill can teach composition conventions.
  • A ComfyUI MCP tool can submit a workflow.
  • A hook can check a changed file.

They may work together because they solve different problems; installing all three is not a prerequisite.

4 · Improve the cause of the failure

{{diagram:improvement-loop}}

Keep the baseline revision and a short reproduction before experimenting.

  • If the intended rule is wrong, revise the brief.
  • If the code violates a sound rule, repair the code.
  • If the implemented experience is dull, test a design hypothesis.
  • If an agent repeatedly misses a procedure, investigate context and selection before adding instructions.

A decision record you can reuse

  • Outcome: what should the player or viewer experience?
  • Evidence: which route, screenshot, clip, or check exposes the problem?
  • Change: what single cause are we testing?
  • Comparison: what improved, and what regressed, under the same scenario?
  • Decision: retain, revise, or restore; link the artifact and revision.

This record is also a good prompt input. Give Astra the observed problem and the review conditions, then let it choose appropriate implementation details.

Save a reusable procedure only after repeated evidence shows that it helps. Next, apply the same approach to an AI-assisted game trailer.
