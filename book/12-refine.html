Refine the idea and the process

Improve the weakest link, then keep what you learned.

When a first build disappoints, resist adding five new features. Decide what kind of failure you have. A wrong mechanic needs a clearer rule. A correctly implemented but dull mechanic needs a design experiment. A broken control needs a reproduction. A forgotten convention needs better repository context.

A worked prompt refinement

The examples below are illustrative revisions, not measured test results.

Use a rubric to expose disagreements

Score each dimension from 0 to 2: 0 means missing or broken, 1 means present but inconsistent, and 2 means demonstrated under the stated test. Add a note and evidence for each score. The score is a conversation aid, not an objective measure of fun.

  • Clarity: the player understands the goal and current state.
  • Control: movement responds consistently and the camera supports it.
  • Completion: the core loop includes win, loss, pause, and reliable restart.
  • Feedback: collection, damage, and beacon readiness are perceivable.
  • Challenge: the route and hazard produce a readable decision.
  • Coherence: visuals, sound, and UI support the same mood.
  • Reliability: the deployed build performs acceptably on the named target.
  • Maintainability: a new session can reproduce the build and find the next change.

Compare approaches with a fair experiment

If you want to know whether your meta-prompt helps, compare it against a direct prompt from the same clean starting revision. Keep the game brief, model, tools, target platform, and effort budget the same. Record which prompt was used and the actual cost, elapsed time, manual interventions, accepted milestones, and regressions.

Judge the playable outputs without looking at which prompt produced them if possible. Repeat more than once before trusting a difference; agent runs can vary. Do not use a single lucky output to declare a universal winner. If one approach uses extra agents or a much larger budget, report that difference instead of attributing the result entirely to wording.

Promote stable improvements

Move a repeated project convention into AGENTS.md. Move a proven review sequence into a skill. Keep a one-off fix in the task’s notes. Update the game brief when playtesting changes the design. This keeps the next prompt short without losing the decisions that make it useful.

For example, “always inspect restart after changing round state” can become part of the game review procedure. “Move this planter two units east” belongs in the current design change. Mixing these together makes reusable instructions noisy.

The retrospective

After a release, write three sentences: which instruction helped most, which failure cost the most rework, and which single change to the workflow you will test next time. Connect each sentence to an actual observation.
