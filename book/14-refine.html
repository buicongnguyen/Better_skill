Refine the idea and the process

Improve the weakest link, then keep what you learned.

Use the Mermaid improvement loop and decision record to make the cause, experiment, and result visible.

When a first build disappoints, resist adding five new features. Decide what kind of failure you have.

  • A wrong mechanic needs a clearer rule.
  • A correctly implemented but dull mechanic needs a design experiment.
  • A broken control needs a reproduction.
  • A forgotten convention needs better repository context.

Use a rubric to expose disagreements

Score each dimension from 0 to 2: 0 means missing or broken, 1 means present but inconsistent, and 2 means demonstrated under the stated test. Add a note and evidence for each score. The score is a conversation aid, not an objective measure of fun.

  • Clarity: the player understands the goal and current state.
  • Control: movement responds consistently and the camera supports it.
  • Completion: the core loop includes win, loss, pause, and reliable restart.
  • Feedback: collection, damage, and beacon readiness are perceivable.
  • Challenge: the route and hazard produce a readable decision.
  • Coherence: visuals, sound, and UI support the same mood.
  • Reliability: the deployed build performs acceptably on the named target.
  • Maintainability: a new session can reproduce the build and find the next change.

Compare approaches with a fair experiment

If you want to know whether your meta-prompt helps, compare it against a direct prompt from the same clean starting revision. Keep the game brief, model, tools, target platform, and effort budget the same. Record which prompt was used and the actual cost, elapsed time, manual interventions, accepted milestones, and regressions.

Judge the playable outputs without looking at which prompt produced them if possible. Repeat more than once before trusting a difference; agent runs can vary.

Do not use a single lucky output to declare a universal winner. If one approach uses extra agents or a much larger budget, report that difference instead of attributing the result entirely to wording.

Keep only improvements that still help

  • A repeated project convention may belong in AGENTS.md.
  • A recurring procedure may merit a skill when existing tools and documentation do not already cover it.
  • Keep a one-off fix in the task’s notes.
  • Update the game brief when playtesting changes the design.
  • Avoid copying the same rule into several layers by default.

For example, loss-before-activation at the same simulation step belongs in the authoritative acceptance document. A review skill can point to it if the agent repeatedly misses that boundary.

“Move this planter two units east” belongs in the current design change. Reevaluate optional guidance after changing the model: a workaround that helped yesterday may be unnecessary today.

The retrospective

After a release, write three sentences: which instruction helped most, which failure cost the most rework, and which single change to the workflow you will test next time. Connect each sentence to an actual observation.

Improve game versions and prompt versions separately

Your proposed loop is useful: build V1, fix it, learn from the prompts, then attempt V2. The correction is to retain prompts plus observed outcomes, not concatenate the conversation.

V2 also inherits better code, assets, and human decisions. Its improvement alone cannot establish that prompt P2 beats P1.

A prompt revision changes supplied instructions; it does not update Astra’s model weights.

  1. Save a baseline. Record commit, prompt version, model settings, tools and skills, and acceptance conditions.
  2. Build and diagnose. Keep failures, successful repairs, evidence, and intervention count.
  3. Extract verified lessons. Separate facts from guesses; drop failed advice and obsolete requirements.
  4. Store each lesson once. Rules go in the brief; regressions in tests; conventions in AGENTS.md; a repeatedly useful procedure may become a skill.
  5. Draft P2. Reference those files and state the next outcome. A shorter prompt can be better.
  6. Compare when the question matters. Give P1 and P2 the same starting commit, files, model, tools, and budget in separate clean runs. Repeat promising comparisons and include a scenario not used to revise P2. Keep main-game development incremental.

For example, a failed restart should produce a regression check and an acceptance rule, then P2 can say “Implement the next milestone and preserve the acceptance rules.” If P2 receives corrected documents that P1 did not, you have tested an improved instruction package, not wording alone.
