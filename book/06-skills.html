Decide whether a skill adds value

Start with what the agent already has. Add what the task is missing.

The claim that project skills can be redundant is partly supported. A skill that repeats general coding advice may contribute little, while a specific workflow can supply knowledge the agent lacks. Automatic skill selection is a capability to use and evaluate; it is not evidence that the agent always selects correctly or produces a better game.

Astra update · 11 September 2026

OpenAI recommends reassessing accumulated instructions for Astra. Overspecified procedures and overlapping skill descriptions can impede useful work. The practical change here is to make custom skills optional, with a specific reason to exist. This is guidance, not a measured Astra skill benchmark. {{cite:17}}

Four different things people call “adding a skill”

  1. Make a skill available. Install or expose it to the agent’s host. A file elsewhere on the internet is not automatically available.
  2. Let the agent select it. Codex supports implicit matching between a task and an available skill’s description. Explicit selection is also supported. {{cite:08}}
  3. Write a new skill. Package a missing reusable procedure, references, or scripts. This is a separate decision from invoking an existing one.
  4. Write repository instructions. AGENTS.md supplies scoped conventions; it is not an on-demand skill selector. {{cite:07}}

Why the studies seem to disagree

SWE-Skills-Bench found little average benefit from public software skills using Haiku 4.5. SkillsBench reports larger gains for curated skills across a broader task mix. Those are different interventions, tasks, and agent configurations. They can both be true. Neither answers whether this particular game-review skill helps Astra. {{cite:22}} {{cite:18}}

Our recommendation: do not create a new skill merely because a tutorial includes that step. First let Astra attempt a bounded task with the information already available. If it misses an existing procedure, inspect selection. If it lacks a recurring piece of project knowledge, supply that knowledge. A prompt correction, a documentation update, or a small script may be sufficient.

A small experiment for your Astra setup

This is a proposed experiment, not a result measured for this book. Use the same starting revision, Astra configuration, tool access, game brief, acceptance checks, and effort budget. Keep required policies in place. Try these conditions in separate clean runs:

  1. Baseline: current available skills, with no extra project skill and no forced skill selection.
  2. Selection check: explicitly select the existing relevant skill. This tests whether routing contributed to the problem.
  3. Content check: keep that same existing skill selected and add one explicitly selected, narrow custom skill. Compare against the existing-skill condition to test the additional information.

For each run, record skill availability and invocation if observable, accepted behaviors, regressions, manual interventions, elapsed time, and token cost when available. Score the same playable routes without knowing the condition if possible. Repeat several runs; retain the extra instructions only if their observed benefit justifies their cost. Once content helps, separately test whether its description allows reliable implicit selection.

An instruction audit

For an optional instruction, ask: which observed failure does it prevent, which fact does it add, and where is the evidence? Shorten, update, or remove it when those answers disappear. If an instruction causes a pause or conflict, identify its exact file and rule before changing it.
