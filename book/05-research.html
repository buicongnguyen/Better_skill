Learn from the evidence

A transcript becomes useful when it changes a decision.

Searching for “best AI game prompt” produces demonstrations, tool promotions, speculative claims, and genuine engineering advice side by side. Read each source for a specific purpose.

Use engine documentation to establish API behavior. Use a creator’s demonstration to learn a process.

Use your own build to find out whether that process works under your constraints.

Transcript notebook: Software Is Changing (Again)

In his Y Combinator keynote, Andrej Karpathy discusses the loop between AI generation and human verification. He argues that concrete requests and auditable intermediate artifacts make that loop more useful, and notes that a huge code diff still leaves substantial review work.

These are conceptual observations, not measured results for game production. {{cite:02}}

Our application: ask for one runnable game milestone with a short list of behaviors to inspect. Put the build link, relevant change, and evidence together.

The person reviewing the game should be able to answer a question such as “Does losing all health always show a restart screen?” without first reconstructing the agent’s entire conversation.

A game tutorial is a separate kind of evidence

GDQuest’s written Godot 4 course and Godot’s own first-3D-game tutorial provide a sequence for learning game structure. Use them to reduce unfamiliarity with the engine. The GDQuest YouTube transcript could not be retrieved reliably during research, so only its accessible written course is used here. {{cite:09}} {{cite:10}}

  1. Do not carry an entire tutorial into a new design unchanged.
  2. Extract one concept, such as movement relative to the camera.
  3. Build a minimal reproduction with the installed engine version.
  4. Then explain how the concept maps to your game, including what must change.

A successful exercise is evidence that you understand one part; it does not validate the whole game.

A repeatable research procedure

  1. Start with a question. For example: “Can the chosen Godot export run on GitHub Pages without custom response headers?”
  2. Find the primary answer. Search official documentation for the installed version; open the page and read the constraints.
  3. Find an applied example. Prefer a creator’s video with an accessible transcript and companion repository.
  4. Record provenance. Save the URL, title, retrieval date, version, and a passage locator. Mark missing captions or an unavailable repository explicitly.
  5. Separate observation from inference. “The tutorial uses this node” is an observation. “This will simplify our camera system” is a hypothesis.
  6. Run one small experiment. Keep the result and the code commit that produced it.
